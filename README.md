**Title:** Risk-Aware Verification Checkpoint Placement for Silent-Error Containment: A Controlled Synthetic Agent-Pipeline Study.

## Read first: what the experiment does and does not establish

This repository includes a **real executed Python experiment** on a **synthetic, controlled agent-pipeline simulator**. It is **not** a deployed language-model agent, a reproduction of numerical results from AgentBench/WebArena/ToolEmu, or proof of performance in production. The initial source paper and review are conceptual papers proposing verification checkpoints; they do not supply an executable baseline or corresponding numerical results. This study is a controlled comparative prototype (assignment pathway B/D), not a replication claim.

The simulation injects at most one syntactically valid semantic fault into one of seven pipeline stages. Each fault must be caught before its prespecified abstract side-effect deadline. A caught fault is repaired with a frozen 90% probability, otherwise the run ends as a safe abort. The rules and evidence checks are separate deterministic validators, and their synthetic trusted fields are assumed correct. Verification costs are **arbitrary abstract units** (rule=1, evidence=1.5); they are **not measured API latency or token usage**.

## Research questions

1. Can a checkpoint schedule selected *only on development scenarios* reduce unsafe terminal outcomes relative to a fixed periodic schedule with the same three-check budget?
2. Does selecting schedules separately by risk context add anything beyond a single risk-optimized schedule?
3. How does removing one kind of verifier affect silent-error containment, and what checking-cost trade-off emerges?

The primary comparison is profile-adaptive vs periodic; global risk vs periodic is a planned secondary comparison. Development and test IDs are disjoint; the final test includes 15,000 cases from seeds 101, 202, 303, 404, 505. Five thousand other generated cases were used for calibration and were not used for the hold-out evaluation.

## Verified execution summary

`results/results.csv` was generated by `scripts/evaluate.py` from `results/trial_outcomes.csv`. A summarized selection:

| Policy | Unsafe rate | Success rate | Mean verification cost |
|---|---:|---:|---:|
| No checkpoint | 59.90% | 40.10% | 0.00 |
| Final-only | 42.31% | 55.96% | 1.44 |
| Periodic (1,3,5) | 8.67% | 86.27% | 7.23 |
| Global risk (2,4,6) | 5.75% | 88.90% | 7.04 |
| Profile-adaptive (both contexts select 2,4,6) | 5.75% | 88.90% | 7.04 |

The adaptive and global schedules are **identical** under the frozen rules. Context routing noise therefore has no influence in this experiment. No advantages of context adaptation are claimed.

## Data structure and checking

`results/test_scenarios.csv` has a unique case ID and ground-truth injection attributes. `results/trial_outcomes.csv` has exactly one row per (case_id, method) pair. `scripts/evaluate.py` refuses duplicated or missing cases, invalid outcomes, missing values, and overlapping dev/test IDs. Metrics are counts or averages on those trial-level records. The bootstrap confidence interval is paired by case ID and conditions on this generator; it is **not** a guarantee about real LLM systems.

## Validation and threats

The source survey's proposed architecture is not a published algorithm with measured performance. Accordingly, baseline validation checks logical invariants and actual execution rather than comparing synthetic percentages to any publication. Key threats: synthetic fault mix and deadlines; only one fault per episode; flawless ground-truth verifiers; externally assigned costs and repair probability; no real LLM calls; no human approval; model/context drift not measured. No randomness in the verifier outputs is claimed. The student should read `docs/technical_review.md` and be able to explain these assumptions before submission.
